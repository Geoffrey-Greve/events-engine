# Implementation brief: Weld Australia feature requests

**Status:** ready to start. Drafted 1 September 2026.
**Source:** Ben Mitchell's letter of 1 September 2026, the 31 August meeting with
Ollie and Danielle, and the open operational list.
**Read first:** `CLAUDE.md` (invariants and Weld business rules), then
`docs/event-worker-spec.md`.

## Ground rules for every task below

From `CLAUDE.md`, non-negotiable. If a task appears to require breaking one, stop
and raise it rather than working around it.

- Never oversell. All seat math goes through the `EventCapacity` Durable Object.
- Seats commit only on payment confirm. A reserve is a TTL hold.
- Every HubSpot side effect goes through the `outbox` table.
- Idempotency everywhere external.
- Multi-tenant from day one. Every row carries `portal_id`.
- The worker makes no direct Xero calls.
- Oversell and waitlist stay human-in-the-loop. The worker never auto-resolves.

Every task ships with tests. Anything touching capacity ships with a concurrent
reserve test. Update the business-rules section of `CLAUDE.md` in the same commit
so the spec does not drift.

# Phase 1 — small, additive, no invariant risk

Ship these first. They are the ones Weld sees quickly.

## 1.1 Capacity guards

**Status: capacity itself is already built.** `events.capacity`,
`ticket_types.capacity` and the `EventCapacity` DO all work. The sold-out
incident was placeholder capacities entered during setup and never replaced, with
one course left at zero. This task stops that recurring.

- Add `events.capacity_unlimited INTEGER NOT NULL DEFAULT 0`.
- Reject create and publish on `POST /events` and `PATCH /events/:id` where
  `capacity` is 0, null or absent unless `capacity_unlimited = 1`. Same for
  `ticket_types.capacity`.
- When an event reaches sold out within 30 minutes of first publish, open a
  `pending_decisions` row (table exists, `0011`) and assign a HubSpot task to
  `events.hubspot_owner_id`, so a human sees it before members do.

**Done when:** an event cannot be published with an unset or zero capacity without
the explicit flag, and a suspiciously fast sell-out raises a decision rather than
silently closing sales.

## 1.2 Attendee contact capture: phone, suburb, state

Today `registrations` carries only `attendee_email` and `attendee_name`.

- Add `attendee_phone`, `attendee_suburb`, `attendee_state` to `registrations`,
  all nullable, backfill NULL.
- Capture at reserve time, persist with the reservation.
- Write back to the HubSpot contact through the **outbox**. Property names come
  from a per-tenant mapping on `tenants`, following the existing pattern set by
  `membership_level_property` and `member_category_property` (`0009_pricing_rules`).
  Do not hardcode property names.

**Conflict handling, and this must not be skipped.** If the contact already holds
a different value, do not overwrite. Write only where the HubSpot property is
empty; otherwise open a `pending_decisions` row. Confirm the exact behaviour with
Ollie before building, because silently overwriting a member's phone number is
worse than not capturing it.

**Done when:** the three fields are captured, persisted, written back where empty,
and a mismatch raises a decision instead of an overwrite.

## 1.3 Staff notes on a registration or order

Staff-entered internal text, distinct from anything the attendee supplies.

```sql
CREATE TABLE registration_notes (
  id              TEXT PRIMARY KEY,
  portal_id       TEXT NOT NULL REFERENCES tenants(portal_id),
  registration_id TEXT REFERENCES registrations(id),
  order_id        TEXT REFERENCES orders(id),
  author          TEXT NOT NULL,   -- HubSpot user id, or 'system'
  body            TEXT NOT NULL,
  created_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
);
```

Append-only. An edit writes a new row. Notes are internal and must never appear on
a ticket, an invoice, or any attendee-facing page or email.

Surface in the manage UI and include in the exports at 2.2.

**Done when:** notes can be added and read against a registration or an order, and
a test asserts they appear in no attendee-facing output.

# Phase 2 — reporting, then questions

## 2.1 Attendance writeback, which unblocks certificates

Ollie has attendance certificates working for membership through HubSpot Data Hub.
Events should feed the same mechanism rather than growing its own certificate
rendering.

- `GET /api/v1/manage/events/:id/attendance` returning per-registration attendance
  state from `tickets` and the check-in records.
- On check-in, write an `attended` flag and an attendance date to the HubSpot
  contact through the **outbox**, using a per-tenant property mapping as in 1.2.

**Do not build certificate rendering, storage or delivery in the worker.** It
duplicates a working mechanism and would give members two different-looking
certificates. Ollie's Data Hub flow takes it from the contact property.

**Done when:** attendance is queryable and lands on the contact, and Ollie can
drive an events certificate from it without further worker changes.

## 2.2 Registration reporting and export

The data is in D1 and written back to HubSpot, but there is no report surface,
which is why the training dashboard numbers are being questioned.

- `GET /api/v1/manage/events/:id/registrations` — full attendee list with ticket
  type, order, payment status, answers (once 2.3 lands), notes and check-in state.
  Paginated.
- `GET /api/v1/manage/events/:id/registrations.csv` — the same as a download. This
  is the one Weld actually asked for.
- `GET /api/v1/manage/reports/registrations?from=&to=&category=` — cross-event
  roll-up by course category and date range.

**Read from D1 directly, never derived from HubSpot.** If the report is built off
HubSpot the numbers will disagree with the engine and the argument repeats.

**Before building:** reconcile the current training dashboard discrepancy with
Ollie. If D1 and HubSpot already disagree, a new report surface makes that visible
rather than fixing it, and it is better to know which is right first.

**Done when:** the CSV matches a hand count for a known event, and the roll-up
reconciles to the per-event lists.

## 2.3 Custom registration questions per event

Dietary requirements is a case of this, not a separate feature. Build the general
mechanism and seed the dietary field from it.

```sql
CREATE TABLE registration_questions (
  id            TEXT PRIMARY KEY,
  portal_id     TEXT NOT NULL REFERENCES tenants(portal_id),
  event_id      TEXT REFERENCES events(id),      -- NULL = tenant-wide default
  key           TEXT NOT NULL,                    -- stable slug, used for mapping
  label         TEXT NOT NULL,
  field_type    TEXT NOT NULL,                    -- text|textarea|select|multiselect|checkbox|phone
  options_json  TEXT,
  required      INTEGER NOT NULL DEFAULT 0,
  scope         TEXT NOT NULL DEFAULT 'attendee', -- 'attendee' | 'order'
  hs_property   TEXT,                             -- contact property to write back, nullable
  sort_order    INTEGER NOT NULL DEFAULT 0,
  archived_at   TEXT
);

CREATE TABLE registration_answers (
  id              TEXT PRIMARY KEY,
  portal_id       TEXT NOT NULL REFERENCES tenants(portal_id),
  registration_id TEXT REFERENCES registrations(id),
  order_id        TEXT REFERENCES orders(id),
  question_id     TEXT NOT NULL REFERENCES registration_questions(id),
  value_text      TEXT,
  created_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
);
```

Rules:

- Answers are captured at reserve time and persisted with the reservation. An
  expired reservation takes its answers with it.
- Questions are versioned by archival, never deleted. An archived question keeps
  its answers readable for past events.
- Where `hs_property` is set, the answer writes back through the **outbox**.
- Validation is server-side in the worker. The HubSpot form or front-end island
  must not be the only place `required` is enforced.

Seed for Weld: `key = 'dietary_requirements'`, `field_type = 'textarea'`,
`scope = 'attendee'`, `required = 0`, tenant-wide.

**Done when:** an event can carry its own questions, answers survive to the
registration, required is enforced server-side, and answers appear in the 2.2
export.

# Phase 3 — amend and cancel

## 3.1 What already exists

More than expected. `0010_refund_transfer` gives `refund_policies`, `transfers`,
`orders.refunded_cents` and `allow_transfer`. **Transfer already reassigns a
registration to a new attendee without refunding: seat kept, ticket reissued,
Marketing Event reassigned.** That covers most of "amend the attendee".

## 3.2 What is missing

- `PATCH /api/v1/manage/registrations/:id` — edit attendee name, email, the 1.2
  contact fields and the 2.3 answers, without a transfer. Re-issue the ticket (new
  `tickets` row, old revoked, QR invalidated) and push a corrected Teams
  registration where `events.provider = 'teams'`.
- `DELETE /api/v1/manage/registrations/:id` — soft cancel. Add
  `registrations.cancelled_at` and `cancellation_reason`.

Constraints on the cancel path:

- **The seat is released through the `EventCapacity` DO**, never by decrementing a
  count in D1.
- Where an order holds several registrations, cancelling one must not cancel the
  order.
- Refund handling is governed by the event's `refund_policy_id`. Do not invent a
  default.
- **A freed seat opens a waitlist decision. It never auto-offers**, per the
  human-in-the-loop rule.

**Done when:** a single registration can be amended or cancelled, capacity and the
waitlist behave correctly under a concurrent reserve test, and the Teams and
HubSpot sides are consistent afterwards.

# Phase 4 — invoice eligibility

## 4.1 The fault is already fixed

Registrations bought on invoice terms were being released before the invoice could
be paid. The hold has been extended. The DO already supports this: `reserve`
accepts a `ttlMs` and `DEFAULT_TTL_MS` is the 15-minute default, so a longer hold
needs no DO change.

**The invariant is intact.** The seat is still held, not committed, so nothing
oversells.

## 4.2 What remains: who qualifies

Model it as a rule, not a flag on a contact, so it is auditable and matches the
existing `pricing_rules` shape.

```sql
CREATE TABLE invoice_eligibility_rules (
  id           TEXT PRIMARY KEY,
  portal_id    TEXT NOT NULL REFERENCES tenants(portal_id),
  match_kind   TEXT NOT NULL,   -- 'membership_level'|'company_property'|'contact_property'|'always'
  match_key    TEXT,
  match_value  TEXT,
  terms_days   INTEGER NOT NULL DEFAULT 30,
  hold_ms      INTEGER,         -- reservation TTL for eligible payers; NULL = default
  min_cents    INTEGER,         -- optional floor, e.g. invoice only above $1,000
  priority     INTEGER NOT NULL DEFAULT 0,
  active       INTEGER NOT NULL DEFAULT 1
);
```

Add `orders.payment_method` (`card` | `invoice`) and `orders.payment_terms_days`.

Resolve most-specific-first, the same way `pricing_rules` resolves. Eligibility is
determined at reserve, so the correct `ttlMs` is passed to the DO on the first
call.

**Hard rule: do not commit a seat on invoice issue.** If anyone proposes it, it
changes a documented invariant and needs a written decision from Ryan first, plus
an explicit carve-out written into `CLAUDE.md`.

**Separately, check the voided-invoice fault.** The D1.1 registration invoice was
voided and could not be paid. Find whether any code path voids rather than
cancels, and make reissue possible from `manage.ts`.

**Done when:** eligibility is rule-driven per tenant, an eligible payer gets the
longer hold automatically, an ineligible one pays at checkout, and no path commits
a seat before payment confirms.

# Phase 5 — module-level registration. Do not start without a decision.

**This is the only genuine product gap on Ben's list, and it is not a toggle.**
`CLAUDE.md` records the current position explicitly:

> "Capacity is event-level + per-ticket-type. No per-session capacity (not in
> scope)."

Registering attendees to individual modules within a course breaks that directly.

## What it requires

- A `sessions` table between `events` and `ticket_types`: an event has many
  sessions, each with `starts_at`, `ends_at`, `capacity`, and optionally its own
  Teams meeting.
- `registrations` gains `session_id`, or a `registration_sessions` join where an
  attendee takes several modules from one course.
- **The `EventCapacity` DO becomes session-aware.** One DO per event holding a map
  of per-session counters is the simpler change and keeps atomicity in one place.
  A DO per session is conceptually cleaner but multiplies coordination on any
  whole-course booking.
- Pricing: is a module priced, or is the course priced and modules are attendance
  only? Weld's HubDB course rows carry course-level pricing today. Separately
  purchasable modules touch `pricing_rules`, the invoice line items and the Xero
  mapping.
- Teams: one webinar per course, or one per module? Per module multiplies Graph
  calls and personal join URLs per attendee.

## Recommendation

Scope this as its own phase with its own decision record. **Give Ben a date for
the decision, not a date for the feature.** Everything else in this brief is days.
This is weeks and it changes a documented invariant.

## Interim, shippable in days, worth offering to Ben

Model each module as its own event with its own capacity, linked to a parent
course via a new `events.parent_event_id`. Attendees register per module. Gives
module-level capacity and reporting without touching the DO, at the cost of a
clumsier purchase flow for whole-course bookings.

# Phase 6 — portal setup: what the app installs into a HubSpot portal

**This phase is not a productisation nicety. Its first slice is already blocking.**
Phases 1.2, 2.1 and 2.3 shipped write-backs that PATCH named contact properties —
`event_attended`, `event_last_attended_date`, `event_last_attended_name`,
`dietary_requirements`, `teams_join_url`. Nothing in the install path creates any
of them. In a portal where they do not exist, those writes fail and the outbox row
goes `dead`. The 2.2 report will then correctly report a gap between D1 and
HubSpot whose cause is that the app never asked the portal for the field.

## 6.0 What install does today, and what it does not

Already built, and not to be rebuilt:

- OAuth exchange → tenant row + stored refresh token (`install.ts`,
  `oauth-callback.ts`).
- `provisionHubDbTables` — creates and publishes the `events` and `ticket_types`
  HubDB tables in the customer portal, idempotently, reusing tables that already
  exist.
- `seedDefaultQuestions` — the 2.3 tenant-wide question set.
- The App Home onboarding wizard: Stripe, Xero GST rate, plan, HubDB tables,
  dynamic-page domain, webinar provider credentials.
- Per-tenant property **mappings** on `tenants` (`contact_phone_property`,
  `contact_attended_property`, `membership_level_property`,
  `voucher_total_property`, …). Every write-back already reads a mapping rather
  than a hardcoded name.

Not built, and the subject of this phase:

| Asset | State today |
| :-- | :-- |
| Custom contact / company properties | Never created. Assumed to exist. |
| Lifecycle workflows | Four markdown specs in `packages/hubspot/src/cms-assets/workflows/`, built by hand |
| Reporting dashboard | Nothing. The 2.2 endpoints exist; no HubSpot surface reads them |
| CRM lists and views | Nothing |
| Dynamic events page | Wizard records a **domain string** and creates nothing |
| Record of what was installed | Nothing. No version, no reconcile, no repair |

**Read `docs/tenant-provisioning-spec.md` before starting.** Its rule stands and
this phase does not relax it: *data* is per-tenant and created in the portal via
API; *code* — the template, the registration module, the App Cards — ships with
the app and is referenced by every portal. Nothing in 6.x copies template or
module code into a customer portal.

## 6.1 Custom properties. Do this one first, out of order if necessary

Provision every property the shipped write-backs assume, create-or-verify,
idempotent, in its own property group so a portal can see what the app added.

Enumerate from the code rather than from this table, because the code is the
source of truth and this list will drift:

| Property | Default name | Object | Written by |
| :-- | :-- | :-- | :-- |
| Attendance flag | `event_attended` | contact | 2.1 `contact.sync_attendance` |
| Last attendance date | `event_last_attended_date` | contact | 2.1 |
| Last event name | `event_last_attended_name` | contact | 2.1 |
| Personal join URL | `teams_join_url` | contact | `contact.set_join_url` |
| Dietary requirements | `dietary_requirements` | contact | 2.3 `contact.sync_answers` |
| Any other 2.3 question | question's `hs_property` | contact | 2.3 |
| Voucher total / used | `vouchers_total`, `vouchers_used` | company | voucher projection |

Phone, suburb and state are deliberately absent: 1.2 defaults them to HubSpot's
**standard** `phone` / `city` / `state`, which every portal already has. Do not
create custom duplicates of them — only a field a tenant has remapped off the
standard property needs provisioning.

Every name in that table is the DEFAULT; each resolves through the tenant's own
mapping first. The join URL was the last hardcoded one and is mappable as of
migration 0026 (`contact_join_url_property`), so nothing the worker writes is
keyed to a name a portal cannot change.

Three rules that make this correct rather than merely convenient:

- **Respect the mapping.** If a tenant has mapped a field to its own property,
  provision nothing for that field — the portal already keys it somewhere. If the
  mapping is `'off'`, the tenant has said they do not want the field written; do
  not create it.
- **Never modify a property that already exists.** A portal may already have
  `dietary_requirements` as a dropdown with its own options. Adopt it, record that
  it was adopted rather than created, and surface a type mismatch to the admin
  instead of resolving it. Changing the type of a property that holds data is
  destructive and is not the installer's decision.
- **A 2.3 question mapped to a property that does not exist should offer to create
  it.** The question editor is exactly where an admin knows what the field means,
  and it is the only point where the app can name the type correctly.

**Scopes: DECIDED — required, and already applied.** Creating properties needs
schema write, which the app did not request at all. Four scopes are now in
`requiredScopes`, not optional:

```
crm.schemas.contacts.read    crm.schemas.contacts.write
crm.schemas.companies.read   crm.schemas.companies.write
```

Required rather than optional because **promoting a scope from optional to required
later forces every installed portal to re-consent, and there is no cheaper moment
than now** — the installed base is one portal. Taking the re-authorisation while
Weld is effectively the only customer is the whole argument.

**The operational consequence: Weld's portal must re-authorise before any of 6.1
can run.** A token issued under the old scope set cannot create a property, and
will fail with a 403 that arrives as a dead outbox row rather than as an error
anyone sees. Re-authorisation is a visit to `/oauth/install`. Do it first; nothing
else in 6.1 works until it has happened.

**The degrade path is still built.** A granted scope can be revoked, and a portal
can decline. Provisioning must report *"cannot create these, here is the list to
create by hand"* and carry on, never fail an install.

**Also fixed while doing this:** the two scope lists — `app-hsmeta.json` and the
worker's `HUBSPOT_OAUTH_SCOPES` — had already drifted. The install URL was omitting
`crm.objects.companies.*` and `crm.objects.tasks.write`, so a portal installed
through it could not read a company's voucher balance or raise an owner task, and
it requested no optional scopes at all, which made the 1.3 note mirror unreachable.
`scripts/check-hubspot-app.mjs` now fails CI on any divergence between the two.

**Done when:** a portal installed from empty can take a booking, a check-in and a
custom-question answer with no manual property creation, no write-back row goes
`dead` for a missing property, and re-running provisioning changes nothing.

### What Weld's portal actually holds (checked 2 September 2026)

From the full property export. This answers the "do the write-back properties exist"
open question, and one row of it is a trap.

| Worker property | Weld's portal | Action |
| :-- | :-- | :-- |
| `event_attended`, `event_last_attended_date`, `event_last_attended_name` | absent | create |
| `teams_join_url` | absent | create |
| `dietary_requirements` (2.3 seed) | absent | create |
| `phone`, `city`, `state` (1.2 defaults) | **all present** | nothing to do |
| `individual_membership_status`, `individual_membership_type_2` | **present** | nothing — membership resolves |
| `corporate_membership_status` / `_level_2`, `industry_supplier_membership_status` / `_level_2` | **present** | nothing |
| `vouchers_total` / `vouchers_used` | **absent — and the data lives elsewhere** | **map first, do not create** |

**The voucher row is the one to act on.** Weld keeps training vouchers in
`vouchers_allowance` and `vouchers_used__training` (plus a separate
`vouchers_used__engineering`, and a calculated `unused_vouchers`). Provisioning an
unconfigured portal would create `vouchers_total` and `vouchers_used`, report them
as created, and leave every corporate booking resolving a **zero balance** off two
empty fields sitting beside the real allowance. Set the mapping BEFORE the first
provision:

```
PATCH /api/v1/manage/onboarding/... voucher_total_property = 'vouchers_allowance'
                                    voucher_used_property  = 'vouchers_used__training'
```

The report now distinguishes an invented name from a chosen one (`source`:
`default` | `mapped`, plus `summary.defaultsToCreate`), so this class of mistake is
visible before the button is pressed rather than after.

**Two things for Ollie, both real decisions:**

- `vouchers_used__training` is already written by a **HubSpot workflow** and feeds the
  calculated `unused_vouchers`. The worker's usage projection would contend with that
  workflow for the same field. Agree who owns it before 6.1 runs against production.
- Contacts already carry `events_attended` — an enumeration of specific event names,
  2.31% filled. That is adjacent to but not the same shape as 2.1's boolean
  `event_attended` + `event_last_attended_name`. Ask whether attendance should append
  there instead of, or as well as, the new pair.

Everything else the worker depends on is present: `hs_tax_rate_group_id` on line
items, `hs_due_date` and `hs_purchase_order_number` on invoices, the task and note
engagement fields, and a `dealtype` carrying both `Event Registration` and
`Training Course`. The Events deal pipeline's Registered stage is `1580881382`.

**Status: built** (`packages/worker/src/properties.ts`).
`GET /api/v1/manage/onboarding/properties` reports without changing anything —
what each property is for, whether it exists, and whether its type can hold what
the worker writes. `POST` the same path creates the missing ones. Creating or
editing a 2.3 question with an `hsProperty` reports whether that property exists
and accepts `createHsProperty: true`, because the question editor is the only
place that knows a `select` needs its options.

The attendance three were briefly provisioned by a second routine in `provision.ts`,
built concurrently with the same rules. That is now removed: the attendance
property DEFINITIONS still live with the feature that owns them
(`ATTENDANCE_PROPERTY_DEFINITIONS`) and the general routine imports them, so there
is one definition and one routine rather than two of each that could disagree.

## 6.2 Lists and views

The saved lists staff actually work from — this year's attendees, no-shows,
awaiting payment — created once at install rather than rebuilt per portal.

- HubSpot's **Lists API** covers saved contact lists and is the reliable half.
- **CRM index-page views** (a saved board or table view on an object) are far less
  well covered by the public API. **Verify what is creatable at build**, and where
  it is not, ship a documented manual step in the wizard rather than pretending the
  installer did it. A setup step that silently did nothing is worse than one that
  says "do this".

**A list is a HubSpot-side derivation and will not agree with the 2.2 report.** A
list of "registered attendees" is built from Marketing Event membership, which
lags the worker by however far the outbox is behind. Say so in the list
description. Do not present a list as the registration count — that is precisely
the argument 2.2 exists to end.

**Done when:** the lists exist after install, each one's description names what it
is derived from, and anything the API cannot create is a named wizard step rather
than a silent gap.

## 6.3 Lifecycle workflows

Today these are four specs — `confirmation-with-ics.md`, `reminder-t7.md`,
`reminder-t1.md`, `no-show-followup.md` — built by hand in each portal.

The workflows README argues they cannot be committed as JSON because **exports**
are portal-scoped: an export embeds owner ids, email-asset ids and branch ids from
the source portal. That argument is about exports and does not apply to an
**API-created** workflow, which resolves its references in the destination portal
at creation time. That distinction is the reason this is now automatable where a
committed JSON blob never was.

- **Verify the Automation API's current create surface at build.** Its coverage of
  enrolment triggers and action types has moved over time, and the whole design
  here depends on what it can express. Where it cannot express a step, create what
  it can and leave the rest as a named wizard step.
- **The email is the portal's, not the app's.** Design, sender, tone and logo
  belong to the customer's brand — that is already the workflows README's contract.
  So the installer creates the **skeleton**: enrolment trigger, timing, branching,
  property reads. Choosing the email asset is a wizard step. An installer that
  invented an email would put Refuel's words in Weld's outbox.
- **The T-1 ordering requirement is a hard one.** `contact.set_join_url` must land
  before the confirmation workflow fires, because HubSpot generates the calendar
  invite. Any created workflow must not enrol before that write-back has drained.

**Done when:** installing into an empty portal produces four workflows in a
paused/draft state with correct triggers and timing, the admin picks an email per
workflow and activates them, and no workflow enrols a contact before its join URL
is written.

## 6.4 The reporting dashboard

**The constraint decides the shape.** `CLAUDE.md`: *"Registration reporting reads
D1 and only D1. Building any of them off HubSpot would make the report disagree
with the engine that sold the seats, which is the argument the surface exists to
end."*

A native HubSpot dashboard built on HubSpot objects reintroduces exactly that
disagreement, in the place staff are most likely to trust it. So:

- **DECIDED: the registration dashboard is an App Card reading the 2.2 endpoints** —
  `GET /events/:id/registrations`, `GET /reports/registrations`, and the CSV export
  token. It is not a native HubSpot report, and that is a decision rather than a
  limitation: a native report would be built on HubSpot objects and would therefore
  disagree with the engine that sold the seats.
- The App Card also removes the dependency on whether custom dashboards can be
  created by API at all, which was the other open question here. It cannot become a
  blocker if nothing depends on it.
- Show the two axes 2.2 already separates and do not add them together: booking
  state (`confirmed` / `awaitingPayment` / `needsReview` / `cancelled`) and
  attendance (`attended` / `registered` / `notYetArrived`). Surface
  `notSyncedToMarketingEvent` prominently — it is the mechanical half of "the two
  systems disagree" and the number this whole phase reduces.
- **Native HubSpot reports stay available and are still right for marketing
  questions** — campaign attribution, Marketing Event performance. They are not the
  registration numbers of record, and the dashboard should not imply they are.

**Done when:** an admin lands in the app and sees this event's numbers and the
cross-event roll-up without leaving HubSpot, the figures equal the 2.2 endpoints
by construction, and the CSV downloads from it.

## 6.5 CMS assets: template, module, page

Restating so nothing here gets "installed" per portal: **the template, the
registration module and the App Cards ship with the app.** They are referenced,
never copied. Fixing one fixes it for every customer, and that is the whole reason
this is an app and not a theme.

The real gaps:

- **The registration module does not render the 1.2 contact fields or the 2.3
  questions.** Both were built worker-side only. The module should read
  `GET /api/v1/events/:slug/questions` and render the returned definitions, using
  each question's `hsProperty` to prefill from the known visitor's own contact —
  which is how "you should not have to type your dietary requirements again" is
  delivered without the worker ever handing out contact data. This is shared app
  code: one build, every portal.
- **The dynamic page stays the wizard click** (`tenant-provisioning-spec.md`
  recommends this and the reasoning holds: domain selection, route collisions and
  publish state are the highest-effort, lowest-reliability part of provisioning).
  But the wizard step must stop **recording a domain string and creating nothing** —
  `hubdb_dynamic_page_domain` is stored, echoed back, and read by no one. Either
  create the page or state plainly that this is a manual step and verify it was
  done.

**Done when:** a public registration form renders an event's custom questions and
contact fields with no per-portal code, and the dynamic-page step either creates
the page or verifies the admin did.

## 6.6 An install manifest, so setup can be repaired and upgraded

Nothing records what was installed, at what version. Without it the wizard's
checkmarks are a claim rather than an observation, an app upgrade that adds a
property has no way to reach existing portals, and there is no answer to "setup is
broken, what is missing?" other than reading the portal by hand.

```sql
CREATE TABLE tenant_installed_assets (
  id           TEXT PRIMARY KEY,
  portal_id    TEXT NOT NULL REFERENCES tenants(portal_id),
  kind         TEXT NOT NULL,   -- 'property'|'list'|'workflow'|'hubdb_table'|'page'|'view'
  key          TEXT NOT NULL,   -- our stable name for it
  hubspot_id   TEXT,            -- what HubSpot called it, once created
  state        TEXT NOT NULL,   -- 'created'|'adopted'|'skipped'|'failed'|'manual'
  version      INTEGER NOT NULL DEFAULT 1,
  detail       TEXT,            -- why it was skipped, or what failed
  checked_at   TEXT NOT NULL,
  created_at   TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
);
```

- `adopted` is distinct from `created` on purpose: a property the portal already
  had must never be treated as ours to change or remove.
- **One idempotent `POST /api/v1/manage/onboarding/provision` that runs everything
  and reports per asset.** "Repair setup" is the same call. A partial failure
  leaves the rest installed and names what failed — an installer that rolls back
  six working assets because the seventh needs a scope is worse than one that
  reports six and a gap.
- **Uninstall removes nothing from the customer's portal.** A property holding a
  member's attendance history is the customer's data, and it is the input to
  Ollie's certificate flow. Deactivate the tenant; leave the portal intact.
  Certification requires honouring HubSpot's uninstall endpoint, which is about the
  app's access, not the customer's records.

**Done when:** the onboarding card shows the real state of every asset, "repair
setup" is safe to press repeatedly, and an app upgrade that adds an asset reaches
portals installed before it existed.

## 6.7 The wizard itself

The six steps exist. What they lack is the difference between *recording an
intention* and *doing the thing and saying what happened*.

- Every step reports: what was created, what was adopted, what was skipped and why,
  what failed and what to do about it.
- A step that requires a scope the portal declined says so, and offers the manual
  alternative — never a checkmark for something that did not happen.
- Publishing stays gated on `status = 'active'` (already built). **Do not gate it
  on setup completeness** — a portal that has not chosen its reminder emails should
  still be able to sell a seat.

**Done when:** an admin can install into an empty portal and reach a first
published event without leaving HubSpot or being told to create a property by
hand, and every incomplete step names what is missing.

2. Phase 1 — 1.1, 1.2, 1.3. Small, additive, visible to Weld quickly.

   it forward if Weld wants those fields on the public form.
